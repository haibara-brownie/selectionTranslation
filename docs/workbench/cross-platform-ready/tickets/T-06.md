Windows 目前**只有模拟 Ctrl+C 一条路**，是三平台里最弱的一环。
参考 Cherry Studio：他们在 Windows 上走 UI Automation + IAccessible + 低级鼠标/键盘钩子，
剪贴板模拟只是兜底。

改成：**UIA 首选 → Ctrl+C 兜底**。

## 必须守住的既有约定

- 抬修饰键那一批事件仍要一次 `SendInput` 发完（约束 4，且 enigo 做不到，所以 Windows
  这边没用 enigo）
- 「Ctrl+C 到底有没有生效」仍靠 `GetClipboardSequenceNumber` 判断，不比对内容

## 已知限制（Cherry Studio 踩过的，可直接借鉴）

JetBrains IDE、Excel/PowerPoint、PDF 阅读器、游戏模式、传统控制台（Ctrl+C 是中断信号）、
UIPI 挡提权窗口。

**注意**：本机（mac）连交叉类型检查都做不了（`aws-lc-sys` 要能编 Windows 的 C 工具链），
只能靠 CI 和用户的 Windows 机器验。写的时候留足日志。

**验收**：用户在 Windows 上按顺序试记事本 / Chrome / VS Code / Word，日志显示 UIA 命中或
正确降级；剪贴板还原正确。

## 已完成（2026-08-20）

### 先解决了「本机验不了」这个前提

票里写着「本机连交叉类型检查都做不了」。**绕过去了**：直接
`cargo check --target x86_64-pc-windows-msvc -p seltrans-core` 确实卡在 `aws-lc-sys`
（reqwest→rustls 的加密后端，要能编 Windows 的 C 工具链），但在 `/tmp/wincheck` 搭一个
一次性壳子——只 `#[path]` 拉进 `selection/windows.rs`、配一个 `logging` 桩、依赖只留
`windows` / `windows-sys` / `arboard`——就能在 mac 上给 Windows 取词代码做**完整的类型
检查和 clippy**。全程用它兜着写，不是盲写。

**这个手法可复用**，下次改 Windows 代码照搬即可。

### 参考来源

Cherry Studio 的划词是独立库 [selection-hook](https://github.com/0xfullex/selection-hook)
（MIT），有中文文档 `docs/zh-CN/WINDOWS.md`。他们的四级回退：
UIA TextPattern → LegacyIAccessible → **沿祖先链重试 TextPattern** → 剪贴板。

### 实现

- **UIA 首选**：`CoCreateInstance(CUIAutomation)` → `GetFocusedElement()` →
  `GetCurrentPatternAs(UIA_TextPatternId)` → `GetSelection()`，多段选区拼接，
  滤掉嵌入对象占位符 U+FFFC。
- **沿祖先链往上找**（最多 10 层，走 `ControlViewWalker`）。**这一步不是可选优化**：
  Chromium / Edge / Electron 里拿到 UIA 焦点的是带 `tabindex` 的容器，选区由祖先的
  Document 元素持有；没有它，浏览器和 Electron 会全部掉进剪贴板兜底。
- **剪贴板兜底先发 `Ctrl+Insert` 再发 `Ctrl+C`**。这条直接治了模块头记的已知限制：
  传统控制台（conhost）里 Ctrl+C 是中断信号不是复制，而 Ctrl+Insert 就是复制、
  也不会打断正在跑的命令。第一发只等 250ms（不响应就赶紧换），第二发给满 800ms。
- **`"primary"` 模式在 Windows 上终于有意义了**：跟 Linux 主选区、mac 辅助功能 API 对齐，
  表示「只走零副作用那条路」，读不到就明确报错，不偷偷动用户剪贴板。原先是静默降级成
  模拟复制。

### 刻意没做的两件

1. **LegacyIAccessible 那一级没实现。** 它服务的是老式 Win32 控件，而那些控件本来就能被
   剪贴板兜底覆盖；代价却是一大块 VARIANT / IDispatch / QueryInterface 的 unsafe 代码，
   而我在本机一行都跑不了。收益不抵风险，留给真机验证之后再定要不要补。
2. **光标形状（I-beam）检测没抄。** 那是给**被动持续监听**用的——selection-hook 要在用户
   划完词的瞬间自动弹工具条，所以得猜「用户是不是在选文字」。seltrans 是按快捷键触发的，
   用户已经明确表达了意图，再用光标形状去猜只会带来误判，还要跟着维护一份应用白名单
   （他们为 Acrobat、CAJViewer 就维护了两份）。

### 依赖变更

引入 `windows` crate（UIA 是 COM 接口，`windows-sys` 得手写 vtable，没人能审）。
只在 `[target.'cfg(target_os = "windows")'.dependencies]` 里，**Linux / mac 的构建完全看不到**，
不影响那边的编译时间和二进制体积。

### 验证状态

- **类型检查 + clippy：已验证**（Windows 目标，`-D warnings` 干净）。
- **运行时：完全未验证。** 需要在 Windows 机器上按顺序试：记事本（老 Win32）、
  Chrome / Edge（要能看到日志里「选区在第 N 层祖先上」）、VS Code、Word、
  cmd/PowerShell（验 Ctrl+Insert 是否解决了控制台取词）、以及提权窗口（应报 UIPI）。
  日志留得很足，每条路线命中哪一级都会打点。
