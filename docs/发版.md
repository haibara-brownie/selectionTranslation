# 发版

从改版本号到用户拿到安装包，全流程。

CI 定义在 `.github/workflows/release.yml`，日常检查在 `.github/workflows/ci.yml`。

---

## 一、发一个版本

### 1. 对齐版本号

三处必须一致，改完一起提交：

| 文件 | 字段 |
|---|---|
| `Cargo.toml` | `[workspace.package] version`（`seltrans` / `seltrans-core` / `seltrans-tauri` 都继承它） |
| `src-tauri/tauri.conf.json` | `version`（安装包上显示的版本，Windows 的 MSI 靠它判升级） |
| `package.json` | `version`（不影响产物，但别让它掉队） |

改完跑一次 `cargo build`，让 `Cargo.lock` 里的版本号跟着更新，否则 CI 上 `--frozen-lockfile` / `--locked` 会报锁文件过期。

**打预发布（rc）时这三处仍写纯 `x.y.z`，只有 tag 带后缀。** Windows 的 MSI 只认三段数字版本号，`0.3.0-rc.1` 这种写进 `tauri.conf.json` 会打不出包。所以是「配置写 `0.3.0`、tag 打 `v0.3.0-rc.1`」，两者不完全一致是有意的。

### 只想在本机出一个平台的包

不打 tag、不走 CI，直接本地打：

```bash
pnpm tauri build --bundles app,dmg     # macOS，产物在 target/release/bundle/
pnpm tauri build --bundles deb,appimage # Linux
pnpm tauri build --bundles msi,nsis     # Windows
```

本机打出来的是**本机架构**。发版 CI 的 mac 那份走 `--target universal-apple-darwin`，Intel 和 Apple Silicon 通吃；本地想要 universal 得先 `rustup target add x86_64-apple-darwin aarch64-apple-darwin`，编译时间大约翻倍。

### 2. 打 tag 并推

```bash
git tag -a v0.2.0 -m "v0.2.0"
git push origin main
git push origin v0.2.0
```

**tag 名必须是 `v` 开头**，workflow 的触发条件是 `tags: ['v*']`。推分支不会触发发版（`ci.yml` 只监听 branches，`release.yml` 只监听 tags，两边不重叠）。

### 3. CI 会做什么

```
create-release  ──►  build (ubuntu-24.04)   .deb / .rpm / .AppImage
     │               build (macos-latest)   .dmg（universal）
     │               build (windows-latest) .msi / -setup.exe
     └─ 先建好草稿 Release，把 id 传给三个 build job
```

- `create-release` 先建一个**草稿** Release，附带写给用户的说明（安装、未签名怎么绕过、已知限制）。这一步单独拎出来，是因为三个 build job 同时起跑，各自去建会撞出三个重复 Release。
- 三个 build job 并行跑 `pnpm tauri build`，产物由 `tauri-action` 自动找出来传到同一个 Release 上。
- `fail-fast: false`：一个平台挂了另外两个照跑完，一次能看清都坏在哪。
- 重跑整个 workflow 是安全的——`create-release` 会先找有没有同名 tag 的 Release，有就复用。

### 4. 产物在哪

GitHub 仓库的 **Releases** 页，状态是 **Draft（草稿）**，只有你自己看得到。

CI **不会**自动发布。检查完产物齐不齐（Linux 3 个 + macOS 1 个 + Windows 2 个，共 6 个文件），点 **Publish release** 才对外可见。

想留退路就先 **Pre-release** 发出去，稳了再取消勾选。

### 5. 本地想看构建产物

CI 的产物在 workspace 根的 `target/` 下（不是 `src-tauri/target/`——这是 cargo workspace，target 目录统一在根）：

```
target/release/bundle/deb/*.deb
target/release/bundle/rpm/*.rpm
target/release/bundle/appimage/*.AppImage
target/universal-apple-darwin/release/bundle/dmg/*.dmg   # mac 走了 --target，多一层
target/release/bundle/msi/*.msi
target/release/bundle/nsis/*-setup.exe
```

## 二、给用户的说明话术

产物**没有代码签名**——没有 Apple 开发者账号（99 美元/年），也没有 Windows 代码签名证书。mac 和 Windows 都会拦。

这段话已经自动写进每个 Release 的说明里（`release.yml` 的 `create-release` job 里那段 heredoc），改文案改那里。原文：

**macOS** —— 首次打开提示「无法打开，因为无法验证开发者」。二选一：

- 在访达里**右键**点 `seltrans.app` → 选「打开」→ 弹窗里再点一次「打开」
- 或者去掉隔离属性：

  ```sh
  xattr -dr com.apple.quarantine /Applications/seltrans.app
  ```

**macOS 的辅助功能授权** —— 划词翻译要读你选中的文字，必须去「系统设置 → 隐私与安全性 → 辅助功能」里勾选 seltrans。第一次按快捷键时系统会主动弹请求。

**升级之后要重新勾一次。** 未签名的应用每次构建出来的代码签名摘要（cdhash）都不一样，系统据此认定「这不是之前授权过的那个应用」，于是把授权作废——表现是升级后按快捷键没反应，看着像程序坏了。签名 + 公证能根治（授权跟着开发者 Team ID 走，不随版本变），但那需要 Apple 开发者账号。发版说明里要把这条讲在前面，别让用户自己去猜。

**Windows** —— SmartScreen 弹「Windows 已保护你的电脑」。点左下角「更多信息」→「仍要运行」。

别把这条说成「小问题」搪塞过去。用户看到的是系统在说这软件不可信，该讲清楚为什么、以及验证途径（构建脚本就在仓库里，可自行编译比对）。

真要根治：mac 需要 Apple Developer Program 账号 + `codesign` + `notarytool` 公证；Windows 需要 OV/EV 代码签名证书。两样都要钱且要年年续，个人工具通常不值当。

## 三、AUR（等有账号之后）

**现在推不了**：AUR 注册通道当时是关的，账号还没到手。在那之前 `packaging/aur/` 只能本地 `makepkg` 自用。

拿到账号之后，每次发版在上面的流程后面补这几步：

```bash
# 1. 算新 tarball 的哈希
curl -sL "https://github.com/haibara-brownie/selectionTranslation/archive/refs/tags/v0.2.0.tar.gz" | sha256sum

# 2. 更新 PKGBUILD：pkgver 改成 0.2.0，sha256sums 换成上面算出来的，pkgrel 重置为 1

# 3. 本地验证 + 重新生成 .SRCINFO
cd packaging/aur
makepkg -f
makepkg --printsrcinfo > .SRCINFO

# 4. 推到 AUR 仓库（和 GitHub 是两个 git 仓库，两边都要推）
cp PKGBUILD .SRCINFO /path/to/aur-seltrans/
cd /path/to/aur-seltrans && git commit -am "更新到 0.2.0" && git push
```

首次推送、SSH 公钥怎么配、AUR 仓库里能放什么，见 [`packaging/aur/README.md`](../packaging/aur/README.md)。

注意 AUR 包打的是 **GTK4 版**，和 GitHub Release 上的 Tauri 版不是同一个二进制。迁移期两版共存的处置理由也在那份 README 里。

## 四、可能踩到的坑

| 症状 | 原因 / 处置 |
|---|---|
| CI 报 `esbuild` 二进制缺失 | pnpm 版本不对。`pnpm-workspace.yaml` 用的 `allowBuilds` 是 pnpm 11 才认的键，装成 10 会被当未知配置忽略，安装脚本被拦。workflow 里已经锁了 `version: 11`，别随手改小。 |
| Windows 上 `aws-lc-sys` 编译失败 | rustls 的加密后端在 Windows x86_64 上要 NASM 汇编器，runner 镜像里没有。workflow 里用 `AWS_LC_SYS_PREBUILT_NASM=1` 走 crate 自带的预编译对象绕开。这招失效的话，加一步 `ilammy/setup-nasm`。 |
| Linux 产物在老发行版上跑不起来 | `.deb` / `.rpm` / `.AppImage` 在 ubuntu-24.04 上构建，需要 glibc ≥ 2.39。不用 ubuntu-22.04 是因为那个 runner 镜像 2026-09-17 起进入弃用期、2027-04-17 彻底下线。要支持更老的系统只能自行编译。 |
| `ci.yml` 的 gtk job 挂了但代码没问题 | 那个 job 跑在 `ubuntu-26.04` 上，目前还是 public preview 镜像。它抽风就临时加一行 `continue-on-error: true`。为什么非得用 26.04 见下。 |
| `cargo build` / `clippy` 在 CI 上「明明没报错但什么都没检查」 | 仓库根 `Cargo.toml` 既是 workspace 根又是一个 package，裸跑只作用于根包，其他 crate 被静默跳过还报 ok。所以 workflow 里一律写 `--workspace`（fmt 是 `--all`），别省。 |
| 本机（Arch 等新发行版）打 AppImage 失败：`unknown type [0x13] section '.relr.dyn'` | linuxdeploy 自带的 `strip` 太老，不认较新工具链生成的 SHT_RELR。加 `NO_STRIP=1` 可以绕过。但**别在本机打 AppImage 发布** —— glibc 只能向前兼容，在新系统上打出来的只能在同样新的机器上跑，CI 的 ubuntu-24.04 才是正确位置。 |
| AppImage 的窗口不浮动 / 行为跟 deb 不一样 | AppImage **跑在 XWayland 上**，不是原生 Wayland：linuxdeploy 的 GTK 插件往 AppRun 里硬塞了 `GDK_BACKEND=x11`（它的注释指向 tauri#8541）。X11 下窗口身份来自 WM_CLASS，app-id 会变成首字母大写的 `Xyz.brownie.…`，`data/niri-snippet.kdl` 的规则已用 `(?i)` 兼容两种。想要原生 Wayland 就装 deb / rpm。 |
| Release 里少了某个平台的产物 | 去 Actions 页看是哪个 build job 红了。`fail-fast: false`，其余平台的产物已经传上去了，修完单独重跑那一个 job 即可，草稿 Release 会复用。 |

### 为什么 CI 要分两个 job

`ci.yml` 里 GTK4 版单独一个 job 跑在 `ubuntu-26.04` 上，纯粹是 runner 镜像的 GTK 版本卡的：

| 镜像 | GTK4 | libadwaita | 够不够 |
|---|---|---|---|
| ubuntu-24.04（= `ubuntu-latest`） | 4.14 | 1.5 | ✗ |
| ubuntu-26.04（preview） | 4.22 | 1.9 | ✓ |

仓库根 `Cargo.toml` 给 gtk4 开了 feature `v4_18`、给 libadwaita 开了 `v1_7`，system-deps 会在构建期硬卡版本，24.04 上直接编不过。所以主检查（core + Tauri，跑在 GA 的 24.04 上）用 `--exclude seltrans` 把根包摘出去，另起一个 job 在 26.04 上单独编它。

迁移 P5 删掉 GTK 代码之后，把 gtk job 整个删掉，主 job 的 `--exclude seltrans` 也一并去掉。
